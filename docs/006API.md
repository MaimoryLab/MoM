## 1. HTTP 端点

### 1.1 当前已实现（Phase 1-2）

| 方法 | 路径 | 用途 | 请求体 | 响应 |
|-----|------|------|--------|------|
| POST | `/v1/messages` | Anthropic Messages 入口，支持 `stream: true` SSE | `AnthropicMessagesRequest` | non-streaming: `AnthropicMessagesResponse`（JSON）<br/>streaming: `text/event-stream` 逐帧输出 Anthropic SSE 事件 |
| GET  | `/dashboard/*` | Vite 构建产物静态挂载（`web/dist/`） | 无 | HTML / JS / CSS 静态资源；构建产物缺失时返回占位 HTML |
| GET  | `/healthz` | 健康检查 | 无 | `{"status": "ok"}` |

**入口协议细节**：

- `/v1/messages` 是网关的**唯一业务路径**。请求最小字段：`model` / `messages` / `max_tokens`（`src/gateway/validator.ts:validateMessagesRequest`）
- `mom_mode === 'always'` 时走 MoM 主链路（fanout advisor → concat references → aggregator）；否则原样透传到 provider
- Body 上限 10 MiB（`src/gateway/server.ts:BODY_LIMIT_BYTES`）
- 错误映射（`src/gateway/messages-handler.ts`）：
  - 400 → 请求体校验失败或 `ValidationError`（Anthropic error JSON: `invalid_request_error`）
  - Provider 原状态码 → `ProviderError`（透传 provider body，能 parse 就 parse）
  - 502 → 未分类的 `gateway_error`
  - Streaming 场景已开始 SSE 写入后遇错 → `event: error` 帧 + `end()`

**Provider 认证**（网关向 provider 发起时）：

- `PROVIDER_AUTH_STYLE=bearer` → `Authorization: Bearer <PROVIDER_API_KEY>`
- `PROVIDER_AUTH_STYLE=x-api-key` → `x-api-key: <PROVIDER_API_KEY>` + `anthropic-version: 2023-06-01`

### 1.2 已规划（Phase 4-6，尚未实现）

| 方法 | 路径 | 阶段 | 用途 |
|-----|------|------|------|
| GET  | `/api/traces?limit=100&offset=0` | Phase 4 | 分页返回 trace summary（不含全量 request/response，避免大 body） |
| GET  | `/api/traces/:id` | Phase 4 | 单条 trace 全量（含 advisor_results / aggregator_result / judge_result / baseline_result） |
| GET  | `/api/metrics?window=last_24h\|last_7d` | Phase 4 | 从 `traces` 表聚合，返回 `Metrics`（含 `total_usage` 分层：advisor / aggregator / judge）、成本 / 延迟 / cache 命中率 / `mom_trigger_rate` |
| GET  | `/api/config` | Phase 4 | 返回当前 `MoMConfig`（**不含 provider 秘钥**，只只读展示 `provider.base_url` / `provider.auth_style`） |
| POST | `/api/config` | Phase 4 | 保存 `MoMConfig`，原子写入 `data/mom.config.json`；触发 hot-reload 或提示重启（机制到 Phase 4 定） |
| GET  | `/api/comparison/:trace_id` | Phase 6 | 返回 `mom_result + baseline_result` 供前端并排展示 |

### 1.3 不会开放的路径

- **无 provider 秘钥编辑端点**：`PROVIDER_*` 只从 `.env` 读，Dashboard 只只读展示（decisions/002 拍板）
- **无 auth 端点**：MVP 假定本地运行、无认证；上线远期版本再加

## 2. 内部 MoM SDK 入口函数（`src/orchestrator/*` + `src/advisor/*` + `src/aggregator/*`）

以下函数是 MoM 业务逻辑的公共入口。**外部项目想复用 MoM 功能，只需要调这些函数、传 `RuntimeConfig` 与 `AnthropicMessagesRequest`**。

### 2.1 主调度入口

```ts
// src/orchestrator/orchestrator.ts
orchestrate(
  body: AnthropicMessagesRequest,
  reply: FastifyReply,
  runtime: RuntimeConfig,
  log: FastifyBaseLogger,
): Promise<void>
```

**当前状态**：签名带 `FastifyReply` / `FastifyBaseLogger`——是 MoM 与网关消息处理层的**唯一耦合点**。参见 §3 解耦评估。

### 2.2 Advisor fan-out

  messages: AnthropicMessage[],

  items: readonly T[],

  worker: (item: T, index: number) => Promise<R>,

// src/advisor/advisor-runtime.ts
runAdvisor(

**已解耦**：以上函数完全**不依赖 Fastify**，只依赖 `MoMConfig` / `ProviderConfig` / Anthropic 类型。

## 3. MoM 与网关消息处理解耦评估

### 3.1 当前耦合面

`git grep -n "FastifyReply\|FastifyRequest\|FastifyBaseLogger\|FastifyInstance" src/` 结果，去掉 gateway/ 本身的合理引用后，业务层耦合集中在 **3 处**：

| 文件（路径:行号） | 耦合点 | 影响半径 |
|---|---|---|
| `src/orchestrator/orchestrator.ts:12-17` | `orchestrate(body, reply, runtime, log)` 签名带 `FastifyReply` + `FastifyBaseLogger`；非流式路径 `reply.send(response)` 由 orchestrator 自己发出 | 主调度入口——最深的耦合点 |
| `src/aggregator/aggregator-runtime.ts:49-58` | `runAggregatorStreaming(original, results, momConfig, provider, reply)` 参数含 `reply`，透传给 provider 层 | 中间层，只做参数透传，不消费 reply |
| `src/provider/stream-forward.ts:8-24` | `passthroughStream(req, reply, provider)` 内部：`reply.raw.setHeader('content-type', 'text/event-stream')` / `reply.hijack()` / `res.body.pipe(reply.raw)` | 最底层，SSE 响应头 + hijack + pipe 三段逻辑都吃 reply |

### 3.2 已经解耦的部分（~80%）

- 所有类型定义（`src/types/*`）— 零 Fastify 依赖
- 所有配置装配（`src/config*.ts`）— 零 Fastify 依赖
- Advisor fan-out 全链路（`src/orchestrator/fanout.ts` + `src/advisor/*`）— 零 Fastify 依赖
- Aggregator non-streaming（`src/aggregator/reference-builder.ts` + `runAggregatorNonStreaming`）— 零 Fastify 依赖
- Provider non-streaming（`passthroughCall`）— 零 Fastify 依赖
- 存储层（`src/storage/db.ts`）— 零 Fastify 依赖

### 3.3 完全解耦需要的改动（估算 ~50 行 diff / 4 个文件）

**思路**：把 `FastifyReply` 换成 Node 标准 `stream.Writable`（`reply.raw` 本质就是 `http.ServerResponse extends stream.Writable`）；把 `reply.hijack()` 与 header 设置上提到 `messages-handler.ts`；`orchestrate` 非流式路径返回 `AnthropicMessagesResponse` 而不是自己 `reply.send`。

具体改动：

1. **`src/orchestrator/orchestrator.ts`**：拆成两个入口
   ```ts
   orchestrateNonStreaming(
     body: AnthropicMessagesRequest,
     runtime: RuntimeConfig,
     log: Logger,          // 自定义最小 logger 接口 { info, warn, error }
   ): Promise<AnthropicMessagesResponse>

   orchestrateStreaming(
     body: AnthropicMessagesRequest,
     runtime: RuntimeConfig,
     output: NodeJS.WritableStream,   // 用 Node 标准接口
     log: Logger,
   ): Promise<void>
   ```

2. **`src/aggregator/aggregator-runtime.ts`**：`runAggregatorStreaming` 参数 `reply: FastifyReply` → `output: NodeJS.WritableStream`

3. **`src/provider/stream-forward.ts`**：
   - `passthroughStream(req, output: NodeJS.WritableStream, provider, onEvent?)` — header 设置与 hijack 从这里剥离
   - 内部 `res.body.pipe(output)` 直接用 `Writable`

4. **`src/gateway/messages-handler.ts`**：承接原本在 orchestrator/provider 层的 Fastify 特定动作
   - non-streaming: `const response = await orchestrateNonStreaming(...)` → `reply.send(response)`
   - streaming: `reply.raw.setHeader(...)` + `reply.hijack()` → `await orchestrateStreaming(body, runtime, reply.raw, ...)`

**估算**：~50 行 diff，4 个文件，**完全不动业务逻辑**，仅做参数类型 & 责任归属调整。

### 3.4 解耦后的使用姿态

外部项目复用 MoM 时：

```ts
import { getConfig } from '@mom/config';
import { orchestrateNonStreaming, orchestrateStreaming } from '@mom/orchestrator';

// non-streaming
const runtime = getConfig('/path/to/mom.config.json');
const response = await orchestrateNonStreaming(anthropicRequest, runtime, myLogger);

// streaming — 直接给一个 Node Writable，例如 http.ServerResponse
await orchestrateStreaming(anthropicRequest, runtime, res, myLogger);
```

- 不需要 Fastify
- 不需要 messages-handler.ts / server.ts / validator.ts
- 只依赖 undici（provider HTTP）+ node:sqlite（trace 落盘）+ node:crypto（cache key，Phase 3 引入）

### 3.5 何时做？

**建议**：随 Phase 3 顺手做一次 refactor commit。理由：

- Phase 3 无论如何都要动 `orchestrate` 与 `passthroughStream`（前者要落 trace，后者要加 observer）
- 顺手把 `FastifyReply` → `Writable` 改掉，比之后专门开一个 refactor 更省事
- 改完后 Phase 4-5 dashboard-api 的接入点也更清晰（`web/*` 前端调 `/api/*`，业务逻辑走 SDK）

**优先级**：P3。当前的 `FastifyReply` 依赖不影响功能，只是"如果要把 MoM 打包成 npm 包给别的项目复用"时会顺带做的事情。ISS-007 记录并跟踪。

## 4. 类型契约

MoM SDK 对外暴露的核心类型都在 `src/types/mom.ts` 与 `src/types/anthropic.ts`：

- **Anthropic 协议类型**：`AnthropicMessagesRequest` / `AnthropicMessagesResponse` / `AnthropicMessage` / `ContentBlock` / `SystemBlock` / `Tool` / `Usage` / SSE 事件族
- **MoM 配置类型**：`ProviderConfig` / `MoMConfig` / `RuntimeConfig` / `AdvisorSettings` / `AggregatorSettings` / `CacheSettings` / `ComparisonSettings` / `ModelPricing`
- **MoM 运行时类型**：`AdvisorResult` / `AggregatorResult` / `JudgeResult` / `BaselineResult` / `Trace` / `Metrics` / `UsageBreakdown` / `FanoutCacheKey` / `FanoutCacheValue`
- **默认值**：`DEFAULT_MOM_CONFIG`

外部项目复用时按需 `import type { ... } from '@mom/types'`。
