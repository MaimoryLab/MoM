# docs/ 文档体系规范

> **AI 协作约定**：每次新对话开始时，请先完整阅读本文件和 `001ARCHITECTURE.md`，
> 再读任务相关的具体文件。未读完本文件前不要对任何文档做修改或给出修改建议。
>
> 项目早期还存在根目录的 `PLAN.md`（当前执行路径），项目启动阶段应优先阅读 `PLAN.md`。
>
> 根目录的 `README.md`（中文）和 `README.en.md`（英文）是面向使用者的项目说明，
> 不属于 AI 协作的核心阅读路径，但在项目初始配置阶段会被修改。

## 文件职责一览

| 文件 | 回答的问题 | 更新时机 | 数量 |
|---|---|---|---|
| `001ARCHITECTURE.md` | 系统怎么运作？模块怎么协作？ | 链路或关键约定变动时 | 永远 1 个 |
| `002STRUCTURE.md` | 代码在哪里？每个文件是干什么的？ | 增删改文件/目录时 | 永远 1 个 |
| `003ISSUES.md` | 现在有什么问题？每个问题处于什么状态？ | 随时追加、随时改状态 | 永远 1 个 |
| `004CHANGELOG.md` | 历史上改了什么？什么时候改的？ | 每次完成改动后追加 | 永远 1 个 |
| `005DEVELOPMENT.md` | 当前版本怎么跑起来？怎么测试？历史配置是什么？ | 测试方式或环境配置有重大变动时 | 永远 1 个 |
| `006API.md` | 有哪些 API？外部调用者/内部模块调用哪些函数？ | 新增/删除 HTTP 路由或 orchestrator 层导出函数时 | 永远 1 个 |
| `decisions/` | 当时为什么这么决定？否定了哪些方案？ | 每次拍板重要决策后新增 | 持续增长 |
| `future-plans/` | 有哪些想法现在不做但将来可能做？ | Plan 接近完成时，或提前识别出来时新增 | 持续增长 |
| `../PLAN.md` | 接下来按什么路径执行？ | 讨论收敛后写，执行完毕后内容迁出 | 永远 1 个 |
| `../README-TEMPLATE.md` | 新项目的 README 应该长什么样？（中英文各一份） | 规范本身变动时 | 永远 1 个 |

## 工作流：一个 Issue 的完整生命周期

不是每个 issue 都要走完全部步骤，按实际情况跳过不适用的阶段。

```
发现问题
  -> 003ISSUES.md 新增条目，状态 [发现]

讨论方案
  -> 003ISSUES.md 同一条目追加方案讨论，状态改 [讨论中]

方案拍板（仅重要决策需要）
  -> decisions/ 新建文件，关联 ISS 编号
  -> 003ISSUES.md 同一条目加关联 decisions/ 链接

开始实现
  -> 003ISSUES.md 状态改 [进行中]

实现完成
  -> 二次核查（见下方「二次核查约定」，强制执行，不可跳过）
  -> 自检自测（见下方「自检自测约定」，通过后代码才算稳定）
  -> 004CHANGELOG.md 追加一条，关联 ISS 编号和 decisions/ 文件（如有）
  -> 003ISSUES.md 状态改 [已解决]，补填解决日期，关联 CHANGELOG 日期
  -> 001ARCHITECTURE.md / 002STRUCTURE.md 按需更新
  -> 执行「交付流程」（见下方章节），输出 PR URL 与本地同步命令
  -> 人工在 GitHub 上 review + merge PR，本地执行 `git pull --ff-only` 拉回 main
```

**简单 bug fix**：`[发现]` -> `[进行中]` -> `[已解决]`，跳过 decisions/

**复杂架构决策**：走完全部步骤

**暂时搁置**：停在 `[暂缓]`，说明原因，其余不动

## 各文件写作规范

### 001ARCHITECTURE.md

**风格：极简陈述，无分析，无立场。**

像地铁线路图——只说线路怎么走，不解释为什么这么规划。

- 用陈述句描述调用链、模块职责、关键约定
- 技术选型只写结论（"用 X 不用 Y"），不写推理
- 只写当前状态，不写历史
- 不写优缺点，不写"这样做的好处是"
- 不写"未来可以考虑"
- 不写被否定的方案
- 不放目录树（目录树属于 `002STRUCTURE.md`）

判断标准：每一句话都应该是当前系统的客观事实。如果一句话需要用"因为"来解释，它不属于这里。

---

### 002STRUCTURE.md

**风格：目录树 + 一句话职责，纯描述，零分析。**

像仓库货架标签——只说这格放什么，不说为什么放这格。

- 目录树结构
- 每个文件/目录一句话说明职责
- 可标注 `# 新增` 或 `# 核心` 辅助定位
- 不写模块之间的关系（属于 `001ARCHITECTURE.md`）
- 不写设计原因

判断标准：一个刚加入项目的人，能否通过这个文件在 1 分钟内找到他要改的代码。

---

### decisions/

**风格：有立场，记录推理，重点写否定了什么。**

像法庭判决书——必须说清楚推理链，尤其是为什么排除了其他选项。

文件命名：NNN-简短标题.md，如 001-scheduler-single-fg-service.md

每个文件使用以下固定格式，字段顺序不可调换：
```
# NNN. 标题（一句话描述这个决策）

**日期**：YYYY-MM-DD
**状态**：已决策
**关联 Issue**：ISS-NNN

## 背景

当时面临什么具体问题。描述触发这个决策的直接原因，
不写系统整体介绍，只写"是什么逼着我们必须做这个决定"。

## 被否定的方案

### 方案 A：方案名称
否定原因：具体说明为什么不能选。必须是客观约束或已验证的问题，
不接受"感觉不好"或"不够优雅"这类理由。

### 方案 B：方案名称
否定原因：同上。

## 最终决策

选择了什么，一句话说清楚。
不写优点，不写"这样更好"——优点已经通过否定其他方案隐含证明了。

## 已知代价

我们知道并接受的副作用。这是给未来的人看的警告，
说清楚"我们不是没想到这个问题，我们是权衡后接受了它"。

每条代价末尾必须显式标注 followup 出口（强制约定，不可省略）：

### 代价 1: 标题
描述。
**Followup**: ISS-NNN | future-plans/NNN-xxx.md | 暂不追踪

合法值仅三种：
- `ISS-NNN`：该代价已 promote 为当下追踪的 issue
- `future-plans/NNN-xxx.md`：已登记为远期演进规划
- `暂不追踪`：明确决定不追踪（代价过小、或属于不可解决的固有限制）

"暂不追踪"是合法选项但需要**明确决定**——这条机制的核心是把"忘了"
变成"决定不追踪"。grep `**Followup**:` 一次能审计所有未追踪的代价。

"不在本期范围"段落（如有）适用相同标注规则。
```
- 不写泛泛的优点（"这样更清晰"——无效信息）
- 不写"未来可以考虑"（在 `003ISSUES.md` 开条目）
- 已写入的决策不修改，只新增
- `关联 Issue` 字段指向触发这个决策的 ISS 编号
- "已知代价" / "不在本期范围" 每条必带 `**Followup**:` 标注，三种合法值之一
- **过渡说明**：Followup 标注规则从本规范引入之日（2026-05-09）起对**新决策**强制生效。
  此前已写入的决策（001-007）不回填、不修改——遵守"已写入的决策不修改"原则；
  其衍生 followup 通过其他途径已部分追踪（如决策 007 的"业务级卡死"已抽出为 ISS-017）

**需要新建 decision 文件的判断标准——满足以下任意一条即开文件：**
- 涉及模块间协作方式、调用链、数据流的变动
- 涉及技术选型（用 A 不用 B，且有多个可选方案）
- 一旦实施后难以回退，或回退成本很高
- 有多个方案被认真讨论过，最终否定了其中一个或多个

**不需要开文件的情况——满足以下任意一条即跳过：**
- 单个 bug 修复，原因明确，没有方案选择
- 改变量名、调整日志格式、补注释等局部改动
- 方案从一开始就只有一个，没有任何分叉

判断标准：六个月后看这个文件，能否清楚知道"为什么不能走回头路"。核心问题永远是：**当时为什么没选方案 B？**

### 003ISSUES.md

**风格：状态驱动，客观描述现象，区分事实与推测。**

像病历——记录症状、严重程度、诊断进展、当前处置状态，不下没有根据的结论。

状态标签：`[发现]` / `[讨论中]` / `[暂缓]` / `[进行中]` / `[已解决]`

优先级标签：`[P0 致命]` / `[P1 严重]` / `[P2 一般]` / `[P3 轻微]`

类型标签：`[崩溃]` / `[功能异常]` / `[性能]` / `[体验]` / `[安全]` / `[技术债]`

每条 issue 使用以下固定格式，字段顺序不可调换：

```
## [ISS-NNN] 问题标题

**状态**：[状态标签]
**优先级**：[优先级标签]
**类型**：[类型标签]
**发现日期**：YYYY-MM-DD

**现象**：
客观描述，附可复现路径。

**后果**：
不处理会发生什么。影响哪些用户 / 场景 / 功能。

**初步判断**：
推测 或 已确认。说明判断依据。

**方案讨论**：（仅 [讨论中] 状态时填写）
方案 A：描述 / 倾向原因
方案 B：描述 / 排除原因
当前倾向：方案 A

**暂缓原因**：（仅 [暂缓] 状态时填写）

**关联**：
-> src/xxx.ts
-> decisions/NNN-xxx.md（如已拍板）
```

已解决的 issue 额外补充：

```
**解决日期**：YYYY-MM-DD
**解决方案**：一句话说明最终采用的方案。
（在原 **关联** 字段追加）-> 004CHANGELOG.md [YYYY-MM-DD-N]

```

优先级定义：
- P0 致命：核心功能完全不可用，或必然导致崩溃 / 数据丢失
- P1 严重：核心功能受损，有概率触发崩溃，或影响大量用户
- P2 一般：非核心功能异常，有 workaround，或影响少数场景
- P3 轻微：体验问题、视觉瑕疵、技术债，不影响功能使用

- 不写最终决策的详细推理（拍板后移入 `decisions/`）
- ISS 编号顺序递增，已解决的条目不删除，状态改为 `[已解决]` 即可，留在原位不移动
- 新增条目追加到文件末尾，不需要读取文件全部内容，因为没有意义
- 写入前只需用 `grep` 获取当前最大序号，在此序号基础上 +1 作为新条目编号，然后把新的内容追加到文件末尾即可

判断标准：任何时候打开这个文件，能否在 2 分钟内看清楚"项目现在有哪些悬而未决的问题"以及"哪些问题最需要立刻处理"。

---

### 004CHANGELOG.md

**风格：类 commit message，简洁列举，不分析。**

本质是"给人读的 git log"——比单条 commit 多一点上下文（涉及文件、关联 issue），比决策文件少很多分析。只记录"改了什么"，不记录"为什么改"。

type 沿用 git 惯例：`feat` / `fix` / `refactor` / `chore` / `docs`

每条记录使用以下固定格式：

```
## [YYYY-MM-DD-N] type(scope): title in English, verb first, one line

### 改动
- 具体做了什么（动词开头）
- 具体做了什么

### 涉及文件
- 文件路径：一句话说明改动方向
- 文件路径：一句话说明改动方向

### 关联字段为必填项，不得省略。
-> ISS-NNN
-> decisions/NNN-xxx.md（如有）
```

- 标题必须英文，动词开头，具体，不超过一行
- 不写原因分析（原因在决策文件里）
- 不写"这样做的好处是"
- 时间倒序排列，新条目插入到文件顶部
- 写入前只需读取第一行获取当前最新条目的日期和序号，在此日期和序号基础上确定新条目编号（同一天则序号 +1，新的一天则序号重置为 1）
- `### 关联` 为必填字段，不得省略。无 decisions 文件时只写 ISS 编号，有则两者都写

判断标准：和 `git log` 对比，信息量稍多但结构一致。

## 二次核查约定

### 核查时机

代码实现完成后，**自检自测之前**执行。核查通过后再跑自检自测，
自检自测通过后代码才算稳定，稳定后再写 CHANGELOG，再走交付流程。

### 核查内容（按顺序执行）

1. **正确性**
   - 逻辑是否正确？
   - 是否存在未处理的边界情况或异常路径？

2. **设计**
   - 改动是否意外破坏了现有的模块职责边界？
   - 是否从第一性原理出发解决问题——
     如果是在原有逻辑上打补丁，必须重构，不得继续。

3. **冗余**
   - 是否存在重复逻辑或可复用但未复用的片段？
   - 是否有无用变量、废弃代码未清理？

4. **健壮性**
   - 异常处理是否采用通用兜底机制（统一错误边界、输入前置校验、
     安全默认值），而不是逐一枚举已知情况？
   - 是否存在只针对当前已知 case 打补丁的防御逻辑——
     如果是，必须替换为覆盖范围更广的通用机制。
   - 如果发现新的边界情况，在自检自测的「增量项」中补充对应的验证脚本

5. **决策衍生项追踪**（仅当本次改动新增或修订 `decisions/` 文件时执行）
   - 扫一遍新决策的 `## 已知代价` 与 `## 不在本期范围`（如有）段落
   - 每一条都必须带 `**Followup**:` 标注，合法值仅三种：
     `ISS-NNN` / `future-plans/NNN-xxx.md` / `暂不追踪`
   - 标注 `ISS-NNN` 的项，确认对应 ISSUES.md 条目已存在或本次同步开新条目
   - 标注 `future-plans/NNN-xxx.md` 的项，确认对应文件存在或本次同步登记
   - 标注 `暂不追踪` 的项，必须有一句话说明为什么不追踪
   - 缺少标注的代价禁止合并——把"忘了"变成"决定不追踪"是这条机制的核心

逐项给出结论（通过 / 发现问题）。
发现问题的项，直接修复，不要只描述问题。
全部通过后，进入「自检自测」；自检自测通过后再写 CHANGELOG 并走交付流程。

### 禁止行为

以下红线由 Claude Code 后台任务硬性约束或本项目明确约定，无论何时都不得跨越：

- 严禁直接 push 到 `main` / `master`；严禁 `--force` 推送。
- 严禁合并 PR；PR 必须以 `--draft` 状态开出，由人 review 后合并。
- 严禁改动 git 配置（`git config`）与跳过钩子（`--no-verify`）。
- 除自建 feature 分支外，不得对他人分支执行 `reset --hard` / `branch -D` /
  `restore .` / `clean -f` 等破坏性操作。
- 自检自测中命令输出的失败信号（非零退出码 / 断言失败 / 编译错误）不得吞掉、
  不得用 `|| true` 或修改断言等方式绕过；失败必须回到「二次核查 - 正确性」
  重新修复，或走「失败终止」分支。

## 自检自测约定

### 执行时机

二次核查全部通过、CHANGELOG 尚未写入前执行。自检失败 → 回到「二次核查」重修；
连续两次失败 → 触发「失败终止」分支，输出失败摘要，不进入交付流程。

### 强制项（每次改动必跑）

- `npm run typecheck`
- `npm run build`
- `npm run build:web`（若本次改动涉及 `web/` 子工作区）

三条命令的退出码必须为 0，任何 warning-as-error 或 tsc 报错都视为失败。

### 增量项（按本次改动追加）

- 本次改动**新引入**的任何验证脚本 / curl 断言 / node -e 断言 / 数据库
  DDL 校验，Claude 必须自己跑一遍并粘贴关键输出；**禁止把新写的验证脚本
  只列在 CHANGELOG 里让用户手跑**。
- 涉及运行时行为的改动（新增路由、修改 provider passthrough、修改
  启动期护栏等），至少启动一次 `npm run dev`，用 `curl` 或
  `node -e` 打关键路径，进程用完关闭。默认端口冲突时用 `MOM_PORT=<空闲端口>`。
- **不主动打真实 provider 接口**——避免消耗 token 与真实 API key。需要
  provider 侧路径覆盖的验证由用户在 review PR 时手动执行，Claude 在 PR
  body 里显式列出「待用户手动验证」的项。

### 输出

在会话里贴出：每条命令的退出码，以及最能证明本次改动生效的 3-10 行输出片段。
不重复贴完整 build log。

## 交付流程约定

自检自测通过、004CHANGELOG.md 追加完成后，Claude 按下列顺序自动执行 Git
提交推送流程。每一步的实际命令与输出（成功或失败）都要贴回会话。

### 1. 提交（worktree 内）

```
git add <明确列出的文件路径，避免 git add . / git add -A>
git commit -m "type(scope): description in English [ISS-NNN]"
```

- commit message 直接复用本次 CHANGELOG 条目标题（已为英文）。
- **subject ≤ 72 字符**（含 type/scope 与末尾 `[ISS-NNN]`）；超长的描述
  塞进 CHANGELOG 的 `### 改动` 或 PR body，不写进 subject。
  长 subject 会被 Claude Code 在 `gh pr create` 时截成 `...`，破坏合并 commit。
- 结尾必须关联 ISS 号：`[ISS-NNN]`。
- 若前后端均有代码改动，两条 commit 分别用各自的 scope。
- 若本次只同步 docs、无代码改动，使用 `git commit -m "docs: sync [ISS-NNN]"`。

### 2. 推送 feature 分支

```
git push -u origin <当前 worktree 的 feature 分支名>
```

- 严禁 push 到 main / master（见「禁止行为」）。
- 分支名沿用 Claude Code worktree 自动生成的名称，不改名、不 rebase。

### 3. 开草稿 PR

```
gh pr create --draft \
  --title "<CHANGELOG 标题，≤ 72 字符>" \
  --body  "<按下方模板填写>"
```

PR body 模板（三段，按顺序）：

```
## Summary
```
